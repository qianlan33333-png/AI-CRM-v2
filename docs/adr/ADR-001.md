# ADR-001：采用模块化单体、角色隔离与固定技术基线

## Status

Accepted — 2026-08-08

## Context

AI-CRM v2 面向单企业私有部署，容量上限约 20 万客户、后台并发不超过 15 人。旧系统的主要问题是模块边界、后台任务和回归防线不足，而不是需要横向扩容。微服务、Redis 或外部 MQ 会增加部署和故障排查成本，偏离单机低运维目标。

同时，仅约定“每个模块有一个 `port.go` 文件”不能形成 Go import 层面的边界：如果 port 与实现处于同一 package，其他模块仍可访问所有导出符号。

## Decision

1. 采用单库模块化单体，交付一个 `aicrm` 二进制，支持 `--role=api|worker|all`。
2. PostgreSQL 16 是唯一有状态组件；River 与业务表使用同库。不引入 Redis、额外消息队列、微服务、读写分离、分库分表或 Kubernetes。
3. 生产建议同机运行独立 api/worker 进程和独立连接池；S 档允许 `all`。api 不注册 worker，worker 不提供业务 HTTP。
4. 每个域的跨模块接口放在独立 package `internal/<domain>/port`。跨域只允许 import `port` 或交换冻结领域事件；`app/store/http/worker` 均为域内实现。
5. `cmd/aicrm` 是唯一 composition root；`internal/platform` 只承载共享基础设施且不能 import 域实现。
6. 固定 Go 1.26.5、Node 24.18.0 LTS、npm 11.12.1、PostgreSQL 16.14，以及 canonical architecture 中列明的依赖版本。业务 Slice 不得顺手升级。

## Consequences

### Positive

- 单次部署和本地调试简单，符合私有化低运维目标。
- api 与重任务故障域、连接池预算可隔离，而不引入分布式系统。
- import 路径可以由 CI 机械验证，避免“文件级接口”形同虚设。
- PostgreSQL 同时提供事务和队列持久化，减少状态组件数量。

### Negative

- 模块不能独立部署或独立扩容。
- 一次二进制发布会携带全部模块，需要契约回放控制回归。
- 独立 `port` package 会产生显式 DTO/接口转换成本。

### Neutral

- 若未来容量或组织结构发生数量级变化，应以新 ADR 重新评估，而不是提前植入微服务兼容层。

## Alternatives Considered

### 传统分层单体

拒绝。部署简单，但不能形成域所有权和跨域依赖边界，无法解决本次重构的核心问题。

### 微服务 + 外部消息队列

拒绝。当前容量和团队协作方式不需要独立扩缩容，其网络、部署、一致性和可观测成本过高。

### 单进程且不区分 role

拒绝。后台同步、群发和统计会与用户请求竞争连接池与内存，重现旧系统的互相拖慢问题。

## Compliance

- CI 必须存在跨域 import 负例并验证失败。
- role 测试必须证明 api 不注册 worker、worker 不开放业务 HTTP。
- 依赖或工具版本变更必须是单独 Slice，并更新本 ADR 或新建 superseding ADR。
