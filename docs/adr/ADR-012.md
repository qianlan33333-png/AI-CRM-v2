# ADR-012：Identity 持久幂等收据与版本化规范化密钥边界

## Status

Accepted — 2026-08-13

## Context

ADR-002～004 与 P3-I00 已冻结渠道中立 OneID、transaction-bound UoW 和
fail-closed 归因，但三张 Identity 业务表尚无正式 DDL。P3-I00 同时要求 Bind、
Ingest 与人工审核命令具备持久幂等；复用 `pending_events` 会把业务待办和技术命令
收据混成一个状态机，进程内幂等又无法承受重启、并发或提交响应不确定。

Identity 还处理可直接识别自然人的原始标识。raw identity、原始
`Idempotency-Key` 和 HMAC key 都不能成为可检索明文或日志内容；旧 key 版本在仍有
历史收据或 fingerprint 引用时又必须保留验证能力。

## Decision

1. Identity 核心业务表保持 `identities`、`customer_merges`、`pending_events`；新增
   identity-owned 技术辅助表 `identity_operation_receipts`。该表不是业务待办，
   不被 pending replay、review 或 River 扫描。
2. raw identity 永不持久化。`normalized_value` 只允许位于
   `identities.normalized_value` 及其精确唯一查询；receipt、result、日志、错误、
   事件、审计文本和快照均不得包含 raw 或 normalized identity。
3. 每条 identity 固定保存 `normalizer_version`。v1 不做 Unicode normalization、
   大小写折叠或默认国家推断；既有行不被未来 normalizer 原地重写。
4. review/audit fingerprint 是 versioned HMAC-SHA256 的前 128 bit，仅用于人工审核
   关联和脱敏展示，不是 Resolve 键，也不是 raw identity 的替代存储。
5. mutation receipt 的逻辑唯一键是
   `(operation, server-derived idempotency_scope, Idempotency-Key)`。scope 只能由稳定的
   已认证 principal/integration 派生，不能使用 `IDRef.Scope` 或请求体字段；物理表只
   保存原始 key 的 32-byte SHA-256 digest。
6. payload HMAC 使用 operation-specific、版本化、长度前缀的无歧义编码，覆盖所有会
   影响结果或审计的命令字段。key 来自 typed deployment secret keyring；当前版本可
   签名，仍被持久行引用的旧版本只能 verify-only 且不得删除。
7. reservation、Identity/Contact/Event 写入、`event_log` 与 completed result 必须在
   同一 UoW。唯一 reservation 算法是
   `INSERT ... ON CONFLICT DO NOTHING RETURNING`：返回行者为 winner；未返回者在同一
   未 aborted transaction 的新 statement 读取 winner 已提交的 completed receipt。
8. 禁止 SELECT-before-INSERT、普通 INSERT 捕获 `23505` 后继续查询、跨 UoW
   reservation/complete，以及提交 `in_progress`。数据库用 deferred constraint
   trigger 在 commit 时拒绝残留 `in_progress`。
9. 同 key 同规范化 payload 返回原闭集 result；异 payload 返回 409 且零副作用。
   未知 state/schema/version、result 越界或缺历史 HMAC key 一律 fail-closed。
10. result 仅允许 status、内部 ID、policy version 与必要时间，JSON object 上限
    16 KiB；不建 GIN/state 索引、不设 TTL，不把 receipt 当业务队列。
11. `40001`/`40P01` 只能有界重试整个 UoW；不能从 reservation 后的中间步骤恢复。

## Consequences

### Positive

- 并发重放、进程重启和提交响应不确定均可返回同一已提交事实。
- 业务待办与技术幂等状态机分离，pending/review worker 不会误消费 receipt。
- raw identity、raw key 与签名密钥具有机械可审计的最小持久化面。

### Negative

- 每个 Identity mutation 增加一次 reservation/complete 写入和 keyring 版本管理。
- 旧 HMAC key 不能仅按时间轮换删除，必须先证明无持久引用。
- loser 会等待 winner transaction 终态，调用方必须有界超时并把数据库错误映射为
  可重试或 fail-closed 结果。

### Neutral

- 该设计依赖当前单 PostgreSQL transaction 边界，不承诺分布式 exactly-once。
- receipt 没有自动清理；未来 retention 只能通过新的 ADR 和离线证明引入。

## Alternatives Considered

### 复用 pending_events

拒绝。它会让技术收据进入业务 replay/review 状态机，并使 TTL、扫描和隐私边界互相
污染。

### 进程内 idempotency cache

拒绝。重启、多进程和提交响应不确定时无法证明原结果。

### 普通 INSERT 捕获 23505 后 SELECT

拒绝。PostgreSQL unique violation 会把当前 transaction 置为 aborted，后续查询得到
`25P02`；不能作为 loser 路径。

## Failure and Test Requirements

- PostgreSQL 16.14 双连接覆盖同 key 同/异 payload，证明 loser transaction 未 aborted、
  只读 completed 原结果且只有 winner 产生副作用。
- 永久负例证明普通 INSERT 的 `23505` 后续为 `25P02`。
- reservation、Identity、Contact、Event、receipt complete 与 commit 各故障点均验证
  全 UoW 回滚；`40001`/`40P01` 验证整 callback 有界重跑。
- migration 必须 clean up/down/up，并验证四表 ownership、约束、索引和 down 清理。
