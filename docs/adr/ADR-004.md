# ADR-004：身份归因与合并默认 fail-closed

## Status

Accepted — 2026-08-08

## Context

AI-CRM 会从企微、公众号问卷、手机号和 Extension 组件接收身份。它们的 scope、来源和可信度不同。把“看起来相同”的标识直接合并会污染客户标签、时间线、群发与自动化；误合并的成本远高于暂时不归因。

原需求中的“先问卷手机号，后加企微好友自动归因”只有在两侧存在可验证的共同桥接键时才安全。单凭时间接近、姓名相同、declared phone 或两个不同 scope 的 openid，不能证明是同一人。

## Decision

1. `IDRef` 必须携带 `Kind`、非空 `Scope`、原始 `Value`、`Assurance`、
   `Source`，并只由 identity 生成内部规范化值。unionid 也必须按微信开放平台
   账号隔离，不能当成跨所有微信主体的全局 ID。
2. `Resolve` 只对精确规范化 identity 工作：唯一客户返回 `found`；无绑定返回 `not_found`；证据冲突返回 `conflict`。它不隐式建客户或合并。
3. 连接两个 identity cluster 必须有可信桥接键：
   - verified unionid 冲突：允许自动客户合并；
   - verified phone 冲突：只创建人工待合并项；
   - declared phone：只作疑似提示；
   - openid：只能在同一 scope 内解析，不能跨 scope 桥接；
   - external_userid 和其他 `ext:*` 标识：只在其定义 scope/来源内使用，不能自动推导跨生态等价。
4. 无可信桥接键时，identity 保持 floating，事件写入 `pending_events`，结果为 `pending`；禁止按姓名、时间、头像或行为相似度猜测归因。
5. 后续 Bind 提供可信桥接后，River worker 可回放 pending event；回放沿用原 `occurred_at`、source 和稳定幂等键。
6. 自动合并仅逻辑归并：被并入客户保留并标记，`customer_merges` 永久追加；任何自动合并均追加 `customer.merged` 事件。自动拆分不在 v1 范围。
7. 结果使用显式枚举：
   - `Resolve`: `found | not_found | conflict`；
   - `Bind`: `bound | already_bound | merged | manual_review | rejected`；
   - `Ingest`: `attributed | pending | conflict`。

## Consequences

### Positive

- 证据不足不会污染客户档案或触发错误外发。
- 冲突和 pending 状态可观测、可审计、可人工处理。
- scope 与 assurance 成为契约的一部分，避免模块间隐含假设。

### Negative

- 部分合法事件会延迟归因，需要等待更多身份或人工处理。
- 产品必须提供 pending/待合并运维能力。
- “问卷后加好友”不能在缺少可信共同键时承诺自动归因。

### Neutral

- identity 可以保留候选关联用于展示，但候选信息不得改变客户数据或触发自动化。

## Alternatives Considered

### 最高分模糊匹配自动合并

拒绝。姓名、头像、时间和自填手机号均可能重复或变化，缺少可接受的误合并回退能力。

### verified phone 冲突自动合并

拒绝。手机号会换主，即使验证过也不等于永久同一自然人。

### 全部冲突都人工处理

拒绝。官方来源的 verified unionid 在同一微信生态内是足够强的桥接键，全部人工会造成无必要运营负担。

## Failure and Test Requirements

- 表驱动覆盖 verified/declared、同/跨 scope、零/一/多命中和重复重放。
- verified unionid 自动合并必须通过 ADR-003 的原子性故障注入。
- verified phone 冲突不得改变任一客户；declared phone 和跨 scope openid 不得创建合并。
- 无桥接键的 survey → wecom 场景必须保持 pending，不能为了通过 happy path fixture 放宽规则。
