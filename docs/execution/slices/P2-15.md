## Service 与事件合同冻结

1. `StageService` 由 `internal/contact/app` 实现；repository 只通过本片私有
   interface 注入，不把 store 类型暴露到公共 port。
2. `ListStages` 在只读 UoW 中调用 P2-14 的确定排序查询；`CreateStage` 与
   `RenameStage` 必须在同一个 UoW callback 内先写 stage，再 append
   `event_log`。任一 repository、payload、clock、key 或 event append 错误都
   回滚完整 callback。
3. 事件类型固定为 `stage.created` / `stage.renamed`；payload 只含
   `stage_id`、`name`、必要时 `sort_order` 与 `actor`，不夹带 config 或外部
   身份；全局 stages 事件的 `customer_id` 为空。
4. 每次事务尝试在 callback 内生成 `stage.<action>:<128-bit random hex>`
   idempotency key，并取一次 UTC `occurred_at`。这样 UoW 因 `40001/40P01`
   重跑且 sequence ID 改变时，不会拿前一已回滚尝试的 key/payload 制造冲突；
   random 或 clock 失败必须回滚，禁止用时间戳单独充当唯一键。
5. 最小输入校验只覆盖架构必需边界：name、actor 必须非空且无首尾空白；
   rename 的 stage ID 必须大于 0；create 的空 config 规范化为 `{}`，非空
   config 必须是合法 JSON。不得自行增加名称唯一、长度、sort_order 正数、
   config object-only 等无证据业务限制。
