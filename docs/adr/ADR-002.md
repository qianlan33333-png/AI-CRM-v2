# ADR-002：以渠道中立 customers.id 作为 OneID

## Status

Accepted — 2026-08-08

## Context

重构详细设计的旧 §2.2 DDL 把 `external_userid` 定义为 `customers` 的非空唯一列，并把 `unionid` 放在客户表；同一文档 §7.1 又明确 `customers.id` 是渠道中立 OneID，所有外部标识都只是 `identities` 的边。这两种模型不能同时成立。

问卷、公众号、企微和未来 Extension 可能先拿到不同外部标识。若客户表以企微 ID 为主键条件，未加企微好友的客户不能自然建档，模块也会各自建立 ID 映射。

## Decision

1. `customers.id` 是唯一内部 OneID，任何业务关联均使用它。
2. v2 第一版 schema 起，`customers` 不含 `external_userid`、`unionid`、openid、phone 等外部身份列；旧 §2.2 相应 DDL 被 §7.1 取代，不采用“先兼容、以后再删”。
3. 所有外部标识只存入 identity 拥有的 `identities`；`customer_id` 可空，以表达 floating identity。
4. identity 唯一键至少覆盖 `(kind, scope, normalized_value)`；scope 是身份含义
   的必填部分，不能忽略。unionid 按微信开放平台账号、openid 按 appid、企微
   external userid 按 corp_id、手机号按 E.164 命名空间隔离。
5. 新客户创建与首个 identity Bind 在同一 transaction-bound UoW 中提交，避免无身份客户或指向不存在客户的绑定。
6. 旧系统迁移必须把客户表中的企微/微信/手机号映射转换为 identity 记录，不得把旧渠道列恢复到新 customers 表。

## Consequences

### Positive

- 核心客户模型不再绑定企微，可承载问卷先行和扩展组件事件。
- 所有模块共享一个身份解析入口，减少重复映射和数据漂移。
- floating identity 与 pending event 可以显式表示证据不足，而不是创建伪客户。

### Negative

- 通过外部 ID 查询客户需要关联 identity 表。
- 迁移必须显式转换旧身份列，并处理冲突或缺失 scope。
- contact 和 identity 的联合写入需要 transaction-bound UoW。

### Neutral

- 企微仍是高权重业务渠道，但不是客户数据模型的主键。

## Alternatives Considered

### 保留 customers.external_userid 作为主身份

拒绝。它排除了非企微先行的客户，并与 Extension/OneID 目标冲突。

### 在 customers 保留冗余身份列以提升查询性能

拒绝作为初始设计。双写会引入一致性来源；只有真实 EXPLAIN/性能证据证明需要时，才可通过新 ADR 引入明确的只读投影。

### 为每个渠道建立独立映射表

拒绝。它让归因规则散落并违反 identity 的独占写入边界。

## Compliance

- schema lint 必须拒绝在 `customers` 新增任何外部身份列。
- 非 identity 模块不得创建或写入 ID 映射表。
- 迁移映射的身份行在 P1 必须人工签字，未签字不能写 live migration。
