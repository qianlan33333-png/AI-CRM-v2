# AI-CRM v2 执行方案（全 AI 开发模式）

> 配套文档：《AI-CRM-v2-重构详细设计.md》（下称"设计文档"），本方案所有任务卡引用其章节号。
> 执行模式：全程 AI coding（Claude Code），无真人工程师。你只承担四类动作：**拍板、核对、企微/服务器人工操作、切换日执行**。
> 排期逻辑：不挂日历，按依赖关系推进。每个阶段有"阶段门"，门不过不进下一阶段。

---

## 0. 全局工作流规范（先于一切任务）

### 0.1 AI 任务标准作业流程

每张任务卡按同一流程执行：

```
1. 开 worktree 分支（沿用你旧仓库的 worktree 脚本习惯）
2. 给 Claude Code 的任务指令固定三段式：
   ┌ 背景：引用设计文档章节号 + 本任务卡编号
   ├ 任务：任务卡"产出物"原文
   └ 验收：任务卡"验收标准"原文 + "完成后输出验证证据"
3. AI 完成 → 提 PR → CI 全绿（P0 建的闸门）
4. 你只看：PR 摘要 + CI 结果 + 任务卡要求的"人工抽查项"
5. 合并。任何 CI 红灯直接丢回给 AI 修，你不 debug
```

### 0.2 并行度纪律

- 同时最多开 **3 个 worktree**。超过 3 个你的 review 会成为瓶颈，且合并冲突概率陡增。
- 同一模块目录同一时间只允许 1 个任务在跑（铁律 §3.2 保证了模块间并行安全）。

### 0.3 AI 开发最高风险三处（验收加倍）

| 风险点 | 原因 | 加倍措施 |
|---|---|---|
| 筛选 DSL 编译器（T3.3） | AI 生成 SQL 拼接逻辑最易出隐性错误 | 表驱动测试 ≥ 50 组 + 与旧系统同条件筛选结果逐一对比 |
| 企微回调验签/解密（T3.2） | AES/SHA1 细节错一位就静默失败 | 用企微官方回调调试工具 + 测试企微真实回调双验证 |
| 迁移字段映射（T5.3） | AI 会"合理脑补"字段语义 | 映射表（T1.4）人工逐行签字后 AI 才许写代码；对账脚本独立于迁移代码开发 |

## P0 基建（串行，一切的前提）

**阶段门：CI 三闸全部生效 + 线上录制开始跑 + dev 服务器可访问。**

### T0.1 新仓库初始化
- 前置：无
- 产出物：新 GitHub 仓库 `AI-CRM-v2`；设计文档放入 `/docs/architecture.md`；`CLAUDE.md` 写入：架构铁律（设计文档 §3.2）、查询规范（§2.3）、容量红线（§1.4）、服务器分档与调优参数（§1.2–1.3）、任务三段式指令模板、"禁止引入设计文档之外的依赖/组件"
- 验收标准：CLAUDE.md 中五条铁律与设计文档逐字一致
- 人工介入：建仓库（5 分钟）

### T0.2 旧系统上线录制中间件 ⚠️ 唯一动旧系统的开发任务
- 前置：无（与 T0.1 并行，**最优先启动**——录制时长决定用例质量）
- 产出物：aicrm_next 的 FastAPI middleware，录制全部 API 请求/响应到本地 JSONL（脱敏：手机号/unionid 哈希化），logrotate 按天切割；部署到线上客户环境
- 验收标准：录制文件格式含 `method/path/query/req_body/resp_status/resp_body/ts`；对线上性能无感（异步写盘）；跑 24h 无异常
- 人工介入：**你确认线上部署窗口并执行部署**（这是对旧生产系统的变更，AI 只出代码不碰生产）

### T0.3 CI 质量闸门
- 前置：T0.1
- 产出物：GitHub Actions 流水线四闸——①`go-arch-lint`（铁律规则文件按设计文档 §3.2 全部八条编写，含"禁跨模块 import""禁自建 timer""禁非 identity 模块写 ID 映射"等符号扫描）②`go test ./... -race` + sqlc 生成物一致性检查 ③迁移文件变更时 `EXPLAIN` 脚本：customers/customer_events 出现 Seq Scan 即 fail ④**契约回放门**（初期为空跑框架，golden case 随功能积累后自动生效）：PR 触及的模块对应 golden case 全量回放，行为变化即 fail
- 验收标准：故意提交跨模块 import 的 PR → CI 红；故意提交全表扫描查询 → CI 红；故意提交一个 `time.Ticker` 业务轮询 → CI 红。三个反例测试永久留仓
- 人工介入：无

### T0.4 环境就位
- 前置：无（并行）
- 产出物：dev + staging 两台轻量云服务器（staging 用 M 档 4C8G 对标标准交付，dev 可用 S 档 2C4G；按设计文档 §1.2 分档表）；**分档部署脚本**（接受 `--tier=s|m|l`，按设计文档 §1.3 参数表自动生成 `postgresql.conf` 与应用环境变量，含 S 档 swap 检查与重任务时间窗设置）；Docker Compose；测试企微主体的回调 URL/可信域名配置指向 staging
- 验收标准：staging 上 `curl /healthz` 通；测试企微回调验证 URL 通过；**同一份脚本在 dev(S档) 与 staging(M档) 分别部署，生成的配置参数与 §1.3 表格逐项一致**（防人工调参出错）
- 人工介入：**买服务器、解析域名、企微管理后台填回调配置**（约 1 小时，只有你有权限）

## P1 行为冻结（人工介入最重的阶段，质量在此决定）

**阶段门：三份清单（API 对照表、功能矩阵、映射表）+ openapi.yaml 全部经你签字冻结。**

### T1.1 API 对照表
- 前置：T0.1
- 产出物：旧系统 `python3 app.py routes` 导出全量路由 → AI 阅读旧代码为每条路由补充：入参、出参结构、副作用、对应新路由命名。产出 `docs/api-mapping.md`
- 验收标准：覆盖 100% 旧路由；每条标注"迁移/合并/废弃"，废弃项必须写原因
- 人工介入：**过一遍"废弃"和"合并"项**（约 30 分钟，其余照单全收）

### T1.2 功能矩阵 ★ 全项目最重要的一张表
- 前置：T0.1
- 产出物：AI 遍历旧前端全部页面代码，产出 `docs/feature-matrix.csv`：`编号 | 页面 | 区块 | 按钮/操作 | 触发的API | 预期结果 | 备注`
- 验收标准：与线上实际页面比对无遗漏
- 人工介入：**你打开线上系统逐页面点一遍，对照矩阵核对增删**（预计 2–4 小时，这是你全程最大的一块人工工作，不可省——矩阵漏一行，新系统就永久缺一个功能）

### T1.3 openapi.yaml v1
- 前置：T1.1
- 产出物：`/api/openapi.yaml`，覆盖对照表全部"迁移"路由，统一 keyset 分页参数、错误结构
- 验收标准：`oapi-codegen` 与 `orval` 均能无报错生成代码；与对照表逐条勾稽
- 人工介入：抽查 10 个核心接口的字段定义（30 分钟）

### T1.4 迁移映射表
- 前置：T0.1
- 产出物：AI 阅读旧 alembic migrations + 模型代码，产出 `docs/migration-mapping.md`：旧表.旧字段 → 新表.新字段，含类型转换规则、默认值策略、丢弃字段清单
- 验收标准：旧库全部业务表被覆盖（明确"迁/不迁"）；丢弃字段逐条写原因
- 人工介入：**逐行签字**（约 1 小时，见 §0.3 风险三）

## P2 平台层（串行两卡）

**阶段门：一个空业务模块的样板（含 API→service→sqlc→事件→测试全链路示例）在 staging 跑通。**

### T2.1 platform 骨架
- 前置：P0 全部 + T1.3
- 产出物：`/internal/platform`（pgx 连接池、River 初始化、chi + oapi-codegen server 装配、结构化日志）、**API 网关中间件**（设计文档 §8.3：请求ID→鉴权→单账号并发预算→超时→panic恢复→统一错误码→结构化访问日志，固定顺序）、**api/worker 角色隔离**（`--role` 三档，各自独立连接池）、**统一 scheduler**（§8.2：唯一 periodic job 注册入口，禁散落 timer）、config 模块（§3.3 强类型配置+启动校验+审计）、events 模块（event_log 写入 + dispatcher 收敛为 River periodic job）、auth 模块（登录/JWT/RBAC 三角色/sales 数据范围过滤）、goose 迁移框架
- 验收标准：故意写错一项配置启动必须失败并指明字段；dispatcher 在 kill -9 重启后不丢不重；`--role=api` 进程不注册任何 worker、`--role=worker` 进程不监听 HTTP 端口（除健康检查）；同账号第 5 个并发请求返回 429
- 人工介入：无

### T2.2 前后端工程接通 + 样板模块
- 前置：T2.1
- 产出物：`/web` 脚手架（Vite/antd/TanStack Query/orval 生成 client/登录页）、`go:embed` 打通、一个"样板模块"（如 stages 管理：列表/新增/改名，五脏俱全含测试）作为后续所有模块的参照实现
- 验收标准：staging 上浏览器登录 → 操作样板模块 → 数据落库 → 时间线出事件，全链路通
- 人工介入：浏览器点一遍样板（10 分钟）

## P3 核心域（最多 3 卡并行）

**阶段门：测试企微上真实完成——同步通讯录、加好友回调建档、按 DSL 圈人、对圈出人群真实发送一条消息。20 万模拟数据灌入后客户列表 P95 < 200ms。**

### T3.1 contact 模块
- 前置：T2.2
- 产出物：设计文档 §2.2 客户域全部表 + §3.3 Service 接口全部实现 + 对应 API + 前端客户中心页面组（列表/详情/时间线/标签/阶段看板，对照功能矩阵相应行）
- 验收标准：功能矩阵 contact 相关行全勾；20 万模拟客户数据（AI 写生成脚本）下列表任意筛选组合 P95<200ms，PR 附压测输出。**压测必须在 S 档（2C4G）dev 机上跑**——最低交付线达标，高档位自然达标；若 S 档不达标，先优化查询而非要求客户升配
- 人工介入：抽查 5 个矩阵行为（15 分钟）

### T3.2 wecom 模块
- 前置：T2.2；与 T3.1 并行，接口对接处用 contact 的 port
- 产出物：回调验签/解密/事件分发（PowerWeChat）、通讯录同步、外部联系人全量+增量同步、wecom_sync_state 游标管理
- 验收标准：企微官方回调调试工具全通过；测试企微真实加好友 → 10 秒内客户建档并出现时间线事件；同步任务中断重跑不产生重复数据
- 人工介入：**用你的微信加测试企微好友做真实验证**（20 分钟，§0.3 风险二）

### T3.3 segment 模块（含 DSL 编译器）
- 前置：T3.1
- 产出物：DSL 编译器（设计文档 §3.3，独立包 + 表驱动测试 ≥ 50 组）、segments/segment_members、刷新 River 任务、前端人群包页面组（列表/条件编辑器/成员预览/手动刷新）
- 验收标准：50 组测试全绿且每组附生成 SQL 的 EXPLAIN；**用旧系统 AI Audience 的 3 个真实人群包定义在新旧系统各跑一次，成员集合 diff 为空**（§0.3 风险一）
- 人工介入：挑 3 个线上真实人群包提供定义，比对 diff 报告（30 分钟）

### T3.4 outbound 模块
- 前置：T3.3
- 产出物：outbound_batches/tasks、令牌桶限速 River worker、失败重试/取消、前端群发页面组（创建/进度/失败重发）
- 验收标准：测试企微对圈选人群真实发送成功；灌 20 万条模拟任务，worker 按配置速率匀速消费、进程重启不丢不重；批次进度数字与实际一致
- 人工介入：手机上确认收到测试消息（5 分钟）

### T3.5 identity 模块（身份图谱，设计文档 §7）
- 前置：T3.1；完成后 T3.2（wecom 建档归因）与后续 T4.2（问卷归因）回接一次改造：外部标识登记全部改调 identity 端口
- 产出物：identities / customer_merges / pending_events 三表、Resolve/Bind/Ingest 实现、unionid 自动合并 + pending 事件回放 worker、后台"待合并"列表页
- 验收标准：造"先问卷手机号建游离身份 → 后加企微好友带 unionid"场景，自动归因且 pending 事件回放落时间线；造 unionid 冲突场景自动合并且 customer_merges 有审计、时间线归并无丢失；**合并逻辑表驱动测试 ≥ 20 组**（自动合并是 §0.3 之外的第四风险点，同级验收）
- 人工介入：在 staging 走一遍"问卷→加好友→自动归并"真实链路（20 分钟）

## P4 上层域（最多 3 卡并行）

**阶段门：功能矩阵 100% 打勾（AI 自查版）。**

### T4.1 automation：触发/条件/动作 + enrollment 幂等 + 前端规则编辑器与记录页。验收：造一条"打标签 X 则发消息 Y"规则，真实回调触发链路 30 秒内完成且重复事件不重复执行
### T4.2 survey + oauth：问卷 CRUD/H5 渲染/提交归因/公众号 OAuth。验收：手机公众号内真实提交一份问卷，正确归因到客户并出时间线事件（人工介入：手机操作 10 分钟）
### T4.3 ai 模块：provider 接口 + 火山引擎实现 + prompts 版本管理 + generations 审计 + 后台 prompt 管理页。验收：改 prompt 版本立即生效；断供（mock 超时）时调用方得到明确错误而非挂死
### T4.4 gateway：MCP 集成边界，按旧 integration_gateway 对外行为迁移。验收：旧 MCP 客户端配置不改指向即可用（对照 API 对照表相应行）
### T4.5 stats：每日预聚合 River 任务 + 数据看板页。验收：看板数字与 SQL 手工核算一致；补跑历史日期幂等
### T4.6 前端收尾：功能矩阵剩余行（系统设置/账号角色等）逐组实现。验收：AI 对照矩阵逐行自查出报告，全部标"已覆盖"并附截图
### T4.7 Extension API（gateway 模块，设计文档 §7.4）：六端点 + API key 鉴权/权限范围/调用审计 + webhook 回推。验收：AI 写一个最小 mock 扩展组件（模拟支付回调，独立进程），通过 Extension API 上报"支付成功"事件 → 正确归因落时间线 → automation 能对该事件配规则触发消息，全链路通；此 mock 组件保留在 `/examples` 作为后续 FDE 定制件的参照模板。注：本卡验收不在功能矩阵内（新增能力），单独对照设计文档 §7.4 端点清单逐条验
### T4.8 运维页（设计文档 §8.4，够用档）：内置单页三块——队列面板（读 River 任务表，含失败任务重试/取消）、接口日志面板（读结构化访问日志，高延迟/错误置顶）、健康自检面板（DB/队列/企微token/AI/扩展key 红绿灯）。验收：手动 kill 一个 worker 后队列面板显示任务堆积、健康面板队列变红；制造一个 500 接口后日志面板可凭 request_id 定位。注：本卡为新增运维能力，不在功能矩阵内，对照设计文档 §8.4 三块逐块验

## P5 验证（回放与迁移，串行为主）

> 注：契约回放自 T0.3 起已作为 CI 门贯穿全程（每个 PR 合并前跑），本阶段是**全量总验收**——把积累数周的全部录制用例一次性回放，而非首次引入回放。这也是根治"改新功能改回老功能"（问题④）的最终确认关口。

**阶段门：契约回放通过率 100% + 两次迁移演练对账零差异 + 你的人工抽验通过。**

### T5.1 contract-replay 工具
- 前置：P4 门；T0.2 已录制的数据（此时应已积累数周）
- 产出物：`tools/contract-replay`——读录制 JSONL，按 API 对照表转换新路由后打向 staging，逐字段 diff（时间戳/自增 ID 白名单），出 HTML 报告；低频接口 AI 补造用例至每接口 ≥ 3 case
- 验收标准：报告能精确到字段级差异定位
- 人工介入：无

### T5.2 回放修复循环
- 产出物：循环执行"回放 → 取 diff → 修复 → 再回放"直至 100%
- 验收标准：连续两轮全量回放 100% 通过
- 人工介入：**每轮看一眼 diff 报告摘要，对"新系统行为是对的、旧系统是 bug"的情况拍板**是修新系统还是接受差异并记录（每轮 15 分钟）

### T5.3 迁移工具 + 演练
- 前置：T1.4 签字版映射表
- 产出物：`tools/migrate-from-v1`（--full/--incremental，upsert 幂等）+ **独立开发的对账脚本**（行数、关键聚合值、随机 100 条逐字段比对——注意：对账脚本必须由独立的 AI 会话开发，不共享迁移代码上下文，防止同源错误互相掩盖）
- 验收标准：staging 上从线上旧库只读副本完整演练 ×2，对账零差异；全量+一次增量总耗时 < 30 分钟
- 人工介入：提供旧库只读账号；看两次对账报告（各 10 分钟）

### T5.4 全功能人工抽验 ★ 你的第二大人工工作块
- 前置：T5.2、T5.3 完成，staging 已灌真实迁移数据
- 产出物：你按功能矩阵在 staging 实际操作核对，逐行打勾/记 bug
- 验收标准：矩阵全勾；bug 清零后重验
- 人工介入：**预计 3–5 小时**。这是唯一一次全量人肉验收，替代的是传统团队里整个 QA 环节，不可压缩

## P6 切换（你主导，AI 出脚本和 checklist）

**前置人工决策：选定首个切换客户并与其约定窗口。**

按设计文档 §6.2 时间线执行，逐条标注执行方：

| 步骤 | 执行方 |
