# P3-C06A：Contact 20 万客户性能验收机制

## 输入合同

- Base SHA：`33f6e19792a6d44686642236fb99d6a4e76c3369`
- Phase：`P3 / contact wave`
- slice_kind：`performance_acceptance_mechanism`
- 决策锚点：`USER-CONTINUE-THROUGH-P4-2026-08-12`
- 目标：用户已授权的 2C4G 低用户量测试服务器；只使用隔离性能数据库，
  不读取或覆盖 staging、legacy 或生产数据。

## 完整行为

1. 提供确定性 synthetic 生成器，在独立 `aicrm_perf` 数据库中生成恰好
   200,000 个渠道中立客户及足以覆盖负责人、阶段、渠道、标签、删除状态、
   加入时间和最近互动时间的分布；不得生成手机号、unionid、openid、
   external_userid 或其他外部身份。
2. 性能验收调用真实 `CustomerQueryRepository` 与 transaction-bound UoW，
   不复制、改写或简化生产 SQL。关键词、负责人、阶段、渠道、标签分别取
   off/on，删除态取 false/true，加入时间与最近互动时间分别取
   none/after/before/closed，页面取 first/next，limit 取 50/200，共
   `2^5 × 2 × 4 × 4 × 2 × 2 = 4096` 个固定组合。next 必须从同筛选首响
   取得真实 keyset，不得伪造 cursor；数据分布必须保证每格都有下一页。
3. 每个组合先预热，再采集至少 20 次完整 repository 调用；每个组合及全局
   P95 均须 `<200ms`。任何一个组合失败即整片失败，不得以平均值掩盖尾部。
4. 对 4096 个组合使用真实生产 SQL 和同一绑定值执行 `EXPLAIN
   (ANALYZE, BUFFERS, FORMAT JSON)`；`customers` 与 `customer_tags` 不得出现
   非预期 Seq Scan，并保存最慢组合、计划节点、buffers 与 timing 证据。
5. 收据只接受目标机事实：2 vCPU、约 4 GiB RAM、PostgreSQL 16.14、S 档
   `shared_buffers/work_mem/effective_cache_size`、200,000 customers 的运行收据。
   本机小数据、CI、mock 或 synthetic 单元测试只能证明工具合同，不能冒充硬门。

## 安全与数据边界

- 生成器必须同时要求数据库名精确为 `aicrm_perf` 与显式 reset token，错误信息
  不回显 DSN；不接受生产数据库、staging 数据库或任意数据库名。
- 性能数据库由测试服务器 PostgreSQL 内新建，迁移后再 seed；不得连接
  `150.158.82.186` 的旧基准数据服务器，也不得读取真实 OneID/身份数据。
- 不修改服务器 S 档参数来追求结果；不升配。若失败，只优化查询/索引并从头重跑。

- 本地：生成器参数/安全边界测试、runner 小数据合同、focused race、SQLc 连续
  生成无 diff、全量 Go/Web/repo-contract/secret 门。
- 目标机：记录精确 main SHA、CPU/内存、PostgreSQL/S 档参数、数据计数与分布、
  4096 组合各自 P95、全局 P95、最慢组合和 EXPLAIN JSON 摘要。
- 中文 PR、squash merge、精确 merge SHA main CI。P3-C06B 必须从这个新 main
  构建 clean exact-SHA 二进制后在目标机执行；Contact 波次只在 C06B 硬门通过后
  才可收口，C06A 合并本身不构成性能通过。

因此验收机制与真实运行不能放在同一个未合并 PR 中。C06A 只交付生成、测量与
收据验证机制；C06B 从 C06A merge SHA 运行授权测试机，提交脱敏证据与必要优化。
