## 冻结行为

- 对输入 refs 逐项执行 I1 的 7 Kind、scope/value 与 E.164 v1 normalizer，再按
  `(kind,scope,normalized_value)` 排序去重；同一 normalized identity 携带相互矛盾的
  assurance/source 直接 fail-closed。ref source 必须与命令 source 相同。
- JSON object payload、refs 顺序、时区和 PostgreSQL 微秒精度先规范化，再进入
  versioned HMAC receipt。相同 key 与相同规范化输入返回首次事实；相同 key 的任一
  规范化字段或 payload 改变都返回幂等冲突，且零新增副作用。
- 同一 UoW 中 upsert 缺失 floating identities；新建 edge 才追加 `identity.created`。
  所有 refs 只导向一个 active root 时，通过 Contact 追加一条客户时间线，并将同一
  业务事件写入 `event_log`，最后完成 `attributed` receipt；返回 customer/event，
  不返回 pending ID。
- 零 root 写 `pending_events(kind=attribution)`；多 root 或不可用 binding 写
  `pending_events(kind=conflict)`。两类 fact 均为 `state=pending/version=1`，保留排序
  identity IDs、event type、规范化 JSON payload、source、原 idempotency key 与原
  occurred_at；随后追加不含 identity value/候选客户/payload 的 pending audit event，
  最后完成 receipt。pending 只返回 pending ID，conflict 不返回候选客户。
- 任一 identity、Contact timeline、pending、event_log 或 receipt 写入失败时，整个
  transaction 回滚；PG16.14 双连接同 key 并发只能提交一个首次事实。
