# ADR-005：Transactional Outbox 采用至少一次投递与业务幂等

## Status

Accepted — 2026-08-08

## Context

客户状态变更会驱动自动化、时间线、外发和 Extension webhook。若先提交业务数据再发布内存事件，进程崩溃会丢事件；若先发布再提交，消费者可能看到不存在的状态。River 能持久化任务并重试，但进程、网络和外部企微 API 仍会造成重复执行或结果不确定。

因此不能把“使用 River”直接表述为 exactly-once。系统必须清楚区分：业务状态与事件的原子记录、至少一次任务执行，以及外部副作用的实际可证明范围。

## Decision

1. 每次状态变更在同一 PostgreSQL transaction 中写业务表与 `event_log`；任一写入失败则整体回滚。
2. `event_log.id` 是事件稳定身份。dispatcher 是 River periodic job，从持久化游标/状态读取未分发事件，不依赖进程内队列。
3. dispatcher 把 event ID 作为 River job 的幂等身份，并在数据库事务中记录分发进度。dispatcher、River worker 和 consumer 均按至少一次语义设计。
4. 每个 consumer 必须使用来源 event ID 或领域定义的稳定 idempotency key，并用数据库唯一约束/状态机防止重复业务效果。只做内存去重不合格。
5. outbound 是唯一企微写 API 出口；wecom 是唯一企微读 API 出口。automation、contact、gateway 等只能调用 outbound `EnqueueOne/EnqueueBatch`。
6. outbound 持久化 task、attempt、结果和远端 ID。对于“请求可能成功但响应丢失”的不确定外部结果，只能根据远端接口提供的幂等或查询能力安全处理；否则保留可审计的不确定状态并进入人工处置，不能盲目重试后宣称不重。
7. 所有周期扫描、重试与分发任务走 River periodic job；禁止业务 `time.Ticker`、`time.AfterFunc` 或第三方 cron。
8. 对外陈述固定为：“基础设施至少一次，业务通过幂等键追求效果不重复”；只有端到端证据覆盖具体接口时，才能对该业务动作作更强保证。

## Consequences

### Positive

- 业务状态与事件不会因进程崩溃而单边提交。
- worker 可安全重启，重复任务有明确的防护责任和审计依据。
- 企微写入收敛到单一模块，限速、重试和日志策略一致。

### Negative

- 每个 consumer 都必须设计并持久化幂等键。
- event_log 与 River 表会增长，需要归档/保留策略和运维可见性。
- 某些外部超时无法自动判定成功或失败，需要人工处置路径。

### Neutral

- event_log 是 transactional outbox，不是事件溯源；业务当前状态仍以域表为准。

## Alternatives Considered

### 进程内事件总线

拒绝。崩溃会丢事件，api/worker 角色拆分后也无法跨进程可靠传递。

### Redis/Kafka 等外部消息系统

拒绝。当前规模不需要其吞吐，且会增加私有部署的状态组件和运维成本。

### 声称 River 提供 exactly-once

拒绝。worker 可在完成副作用后、确认任务前崩溃；网络超时也会造成外部结果不确定。

### 由各模块直接调用企微

拒绝。会产生多套限速、重试、审计和幂等策略，无法统一验证。

## Failure and Test Requirements

- 在业务写、event append、River enqueue、consumer 处理和确认之间逐点 kill/fault injection。
- 重复投递同一事件，验证数据库业务效果不重复且审计保留尝试记录。
- role 重启后未处理事件最终可继续处理；不能使用内存状态才能通过的测试。
- 静态检查必须拒绝非 outbound 的企微写 client、非 wecom 的企微读 client，以及业务 timer。
- synthetic 测试不得冒充真实企微端到端 exactly-once 验证。
