## 2. 模块移植协议（编排层强制，P3 起适用）

> 定位：旧代码是**最完整的行为真相**（含多年积累、从未入文档的边界处理与企微 API 怪癖补丁），必须利用；旧架构是本次重构要摆脱的对象，绝不能复刻。因此采用**参照移植**，严禁**逐文件直译**。

**分界线**

| 必搬（业务规则，旧代码是唯一真相） | 必重写（骨架，旧实现即病灶） |
|---|---|
| 阶段流转判定条件 | 路由 / 中间件 / 鉴权 |
| 标签与自动化规则细节 | DB 访问层（schema 已重构） |
| 问卷题型结构与校验逻辑 | 任务调度（散落 timer → River periodic job） |
| AI prompt 模板与输出后处理 | ID 映射（→ identity 模块统一承接） |
| 企微字段解析与映射细节 | 外发调用（→ outbound 模块独占） |
| 各类派生计算、历史边界分支 | 配置读取（→ config 强类型注册表） |

**两阶段**

- **阶段 A｜规则提取**：只读旧 Python，产出 `docs/rules/{module}.md`，三段结构——①业务规则清单（每条标注旧文件+行号，特别标出"看起来奇怪但确实存在"的分支，这类多为历史 bug 修复，最不能丢）②骨架代码识别（标"不移植，按新架构重写"）③需改造点（涉及外部 ID → 标注改调 identity port；周期执行 → 改 River periodic job；直调企微写接口 → 改走 outbound）。**本阶段禁止输出任何 Go 代码。**
- **阶段 B｜实现**：**必须新开会话，且不提供旧 Python 源码。** 输入仅为 `docs/rules/{module}.md` + 设计文档 + 冻结的 OpenAPI。代码组织必须按设计文档 §3.1，禁止按旧文件结构组织。

**P1 已产出的 `docs/evidence/p1/api-facts-*.md` 视为阶段 A 的等价产出**，P3 实现前按模块重整为 `docs/rules/{module}.md` 即可，不重复盘点。

**违规信号（review 一眼可查）**：新模块目录出现与旧项目同名文件；Go 代码出现 Python 式动态 map 传参；函数调用链与旧代码高度同构。出现任一 → 该片打回重走阶段 B。

## 5. P2：平台层（约 18 片）

**目标（一句话）：P2 结束时，浏览器里必须有能点的东西。**

如果 P2 全部做完你仍只能 `curl /healthz`，说明跑偏，立即叫停并砍流程。

### 5.1 片组与顺序

| 组 | 片 | 说明 |
|---|---|---|
| A 事务与配置 | UoW、强类型 config、settings/secret 存储 | UoW 是 ADR-003 的落点，contact/identity 联合写入的基础 |
| B 队列与事件 | River role 装配、scheduler 唯一注册入口、event 追加、dispatcher | scheduler 必须是**唯一** periodic job 注册点（铁律 8） |
| C HTTP 面 | 请求/错误中间件、并发预算、登录、RBAC、router | 中间件顺序按设计文档 §8.3 固定：请求ID→鉴权→并发预算→超时→panic恢复→统一错误码→结构化日志 |
| D 前端壳 | Web shell（布局/路由/登录页/侧边栏） | 侧边栏数据走 60s 进程内缓存（设计文档 §8.1） |
| E 样板模块 | stages store / service / handler / page | **后续所有模块的参照实现**，五脏俱全含黑盒测试；产出**首组真实行为快照**（§9.5） |
| F 部署与分档 | 分档配置生成 + Docker Compose + staging 部署脚本 | G2 的硬前置：`--tier=s\|m\|l` 按设计文档 §1.3 参数表自动生成 `postgresql.conf` 与应用环境变量，杜绝人工调参 |

### 5.2 P2 出口标准（G2）

- `--role=api` 进程不注册任何 worker；`--role=worker` 不监听业务端口（除健康检查）
- 同账号第 5 个并发请求返回 429
- 故意写错一项配置 → 启动失败并指明字段
- dispatcher `kill -9` 重启后不丢不重
- 同一份部署脚本在 dev(S 档) 与 staging(M 档) 分别执行，生成的配置参数与设计文档 §1.3 表格逐项一致
- **G2 外部门（人工，需我单独授权部署）**：staging 浏览器登录 → 进入 stages 页 → 新增一个阶段 → 列表出现 → 改名 → 生效。全链路真人操作通过。

## 6. P3：业务核心（本版重点）

### 6.1 波次与依赖

```
波次 1（串行，地基）      contact
                            │
波次 2（并行）      ┌───────┴───────┐
                 identity        segment
                    │               │
波次 3（并行）      ▼               ▼
                  wecom          outbound
```

- 依据：segment 的筛选只依赖 customers 实体列与 tag，不依赖 identity；outbound 的批量展开依赖 segment 成员表。
- 并行前置（AGENTS.md 要求）：对应域的 OpenAPI 与公共 port 已冻结。波次 2 启动前须冻结 identity + segment 契约；波次 3 启动前须冻结 wecom + outbound 契约。
- 最多 3 个并行任务，与规模上限同属附录 A。

### 6.2 波次 1：contact

**目标行为**：客户档案的读写与时间线，成为全系统唯一的客户写入方。

| 片 | 可观察行为 | 关键约束 |
|---|---|---|
| C-1 | 客户列表查询（store+service+handler+黑盒） | keyset 分页；禁 `COUNT(*)`、禁深 OFFSET；总数 >1万 走估算 |
| C-2 | 标签与阶段写入 | 与 `event_log` 同事务（铁律 4）；actor 记录 |
| C-3 | 分区时间线 | 按月 RANGE 分区；启动任务预建未来 3 个月；BRIN + (customer_id, occurred_at DESC) |
| C-4 | 客户列表 UI | 对照功能矩阵对应行 |
| C-5 | 详情 / 操作 UI | 同上 |
| C-6 | 20 万数据性能验收 | 见下 |

**专项控制**
- `customers` 表**不得**出现任何外部身份列（ADR-002），schema lint 必须拦。
- C-6 压测**必须在 S 档（2C4G）dev 机执行**：20 万模拟客户，任意筛选组合 P95 < 200ms，PR 附 `EXPLAIN` 与压测输出。S 档不达标 → 优化查询，不得要求升配。
- M0-3 的 EXPLAIN 门在本波次首次承载真实业务查询，任一 Seq Scan 即红。

**出口**：功能矩阵 contact 相关行全勾；C-6 达标；contact port 冻结（波次 2 依赖）。

### 6.3 波次 2A：identity（**全 P3 最高风险模块**）

**为什么风险最高**：无旧代码对应（纯新增），且合并逻辑一旦错误会产生**不可逆的数据污染**——两个客户被错误合并后，标签、时间线、归属已经归并，回退需人工工单。

| 片 | 可观察行为 |
|---|---|
| I-1 | 标识规范化 + upsert（scope 命名空间按 ADR-002：unionid→开放平台账号 / openid→appid / external_userid→corp_id / phone→E.164） |
| I-2 | Resolve（查不到返回 found=false，**禁止隐式建档**） |
| I-3 | Bind（含冲突检测分流） |
| I-4 | 自动合并（仅 verified unionid 冲突） |
| I-5 | Ingest（归因成功落时间线 / 失败入 pending_events） |
| I-6 | pending replay worker |
| I-7 | 人工待合并 API |
| I-8 | 待合并页面 |
| I-9 | 并发负例 |

**专项控制（验收加倍）**
- 合并逻辑**表驱动测试 ≥ 20 组**，覆盖：主记录选择、标签并集、时间线归并、`customer_merges` 审计完整性。
- **并发负例必做**：同一 unionid 的两个 Bind 并发提交，不得产生重复合并或孤儿绑定；用真实 PG 事务测（非 mock）。
- fail-closed（ADR-004）：无唯一可信归因时必须保持 floating identity / pending event，**禁止猜测**。verified phone 冲突进人工队列；declared phone 与跨 scope openid 不得自动桥接。
- contact ↔ identity 联合写入必须走 transaction-bound UoW（ADR-003），禁止跨域直写。

**出口**：I-1..I-9 全绿；场景验收——"先以手机号建游离身份 → 后加企微好友带 unionid → 自动归因且 pending 事件回放落时间线"在 staging 跑通。

### 6.4 波次 2B：segment（**AI 生成代码风险最高处**）

| 片 | 可观察行为 |
|---|---|
| S-1 | 筛选 DSL 的 AST 定义与解析 |
| S-2 | DSL → SQL 编译器 |
| S-3 | 每条生成 SQL 的 EXPLAIN 验证 |
| S-4 | 成员物化刷新（River periodic job） |
| S-5 | handler |
| S-6 | 人群包 UI（列表/条件编辑器/成员预览/手动刷新） |

**专项控制**
- 编译器**表驱动测试 ≥ 50 组**，每组附生成 SQL 的 `EXPLAIN`。
- **与旧系统对拍**：取线上 AI Audience 的 3 个真实人群包定义，新旧各跑一次，成员集合 diff 必须为空。这是唯一能证明筛选语义一致的客观标准。
- 可筛字段白名单 = customers 实体列 + tag。新增字段必须同时"加列 + 加索引 + 进白名单"三件套。
- 编译器是**唯一**的"筛选→SQL"转换代码，segment 刷新与后续 automation 条件判断共用，禁止第二份实现。

**出口**：50 组测试全绿；3 个真实人群包 diff 为空（需你提供定义）。

### 6.5 波次 3A：wecom

| 片 | 可观察行为 |
|---|---|
| W-1 | 回调验签 / AES 解密 |
| W-2 | 回调去重（幂等键） |
| W-3 | token 管理 + read client |
| W-4 | 通讯录 / 外部联系人同步（游标续跑） |
| W-5 | identity / contact 集成（建档与归因） |

**专项控制**
- 验签/AES 是 §0.3 三大风险之一（错一位静默失败）：企微官方回调调试工具 + 测试企微真实回调**双验证**。
- 同步中断重跑不得产生重复数据（`wecom_sync_state` 游标幂等）。
- 企微读 API 只允许本模块调用（铁律 3），lint 已在 P0-S08 落地。

## 9. 回归防线：行为快照测试（替代契约回放）

> **路线变更依据**：旧系统只保留 API 调用元数据，无历史请求体与响应体，真实契约回放缺乏素材。原 v1 §5 的 golden case 录制回放路线**作废**，改为本章方案。

### 9.1 为什么必须有替代方案

"改新功能把老功能改回"是本次重构要根治的四大痛点之一（设计文档 §8.5）。架构 lint 防的是"乱 import"，**防不住行为悄悄变了**。没有回归防线，P4 做 automation 时改坏 P3 的 contact，CI 全绿也发现不了。

### 9.2 方案：随片沉淀的行为快照

**核心机制**：每片交付时，把该片核心接口的输入输出固化为快照文件存入仓库；此后任何 PR 若改变这些接口的行为，CI 逐字段 diff 立即变红。

- 快照位置：`acceptance/snapshots/{module}/{operation}.json`
- 内容：请求（method/path/body）+ 期望响应（status/body），时间戳、自增 ID 等易变字段进白名单忽略
- 数量：每个核心 operation ≥ 3 组（正常 / 边界 / 错误）
- 生成方式：由该片的黑盒验收测试产出，**不得手写**；重新生成必须无 diff

### 9.3 与契约回放的能力差异（诚实记录）

| 维度 | 真实契约回放（已作废） | 行为快照（本方案） |
|---|---|---|
| 防新旧行为不一致 | ✅ 能 | ❌ **不能** |
| 防新系统自身回归 | ✅ 能 | ✅ 能 |
| 素材来源 | 旧系统真实流量 | 新系统验收测试 |
| 同源盲区 | 无 | **有**：快照由 AI 对旧行为的理解生成，理解错了快照也跟着错 |

**结论**：本方案只解决"回改"，不解决"新旧不一致"。后者的唯一保障转移到 **G1 签字的 API 事实盘点 + P5 的人工全功能抽验**——这两处的权重相应上升，不可压缩。

### 9.4 CI 接线

- P0-S10 已落地的空 contract-replay 结构门**复用为快照门**，改名 `snapshot-gate`，不新建机制。
- 触发条件：任一 PR 改动 `internal/**` 时，全量跑快照比对。
- 快照变更规则：**任何快照 diff 必须在 PR 说明中显式解释**（是有意的行为变更还是回归）。有意变更需同步更新快照文件并在 slice 卡记录原因；无解释的 diff 一律视为回归，打回。

### 9.5 落地时点

- **M0 之后、P2 之前**新增一片 `M0-5`：把 P0-S10 的空回放门改造为快照门框架 + 永久负例（一个故意改变响应字段的提交必须让 CI 红）。
- P2 的 stages 样板片产出**第一组真实快照**，作为后续所有模块的参照格式。
- P3 每个模块的 handler 片必须附带该 operation 的快照，无快照不予合并。

## 附录 B：G1 路由分级作业规程（781 条）

**目标**：把不可能的逐条签字压成可行的批量决策。

| 档 | 判据 | 处置 | 你的动作 |
|---|---|---|---|
| **A** | 现有 API 调用记录中有真实流量 | 逐条决策迁移/合并 | 逐条看（预计 100–200 条） |
| **B** | 源码存在、零流量、且无 UI 引用 | 默认废弃 | 扫清单，批量确认 |
| **C** | 源码已标 retired / blocked / fixture / 恒定 404·410 | 默认不迁 | 扫清单，一次确认 |

**执行**
1. 你从旧系统现有 API 调用查询能力导出**路径级频次表**（路径 + 调用次数 + 最近调用时间，建议覆盖 ≥ 30 天窗口），交给 AI。元数据即可，无需请求体/响应体。
2. AI 结合频次表 + 功能矩阵的 UI 引用关系，对 781 条自动打档，产出 `docs/evidence/p1/route-triage.md`（每条注明判据来源与命中的频次数据）。
3. 你先过 C 档（最快）、再过 B 档、最后逐条过 A 档。
4. 任一档中存在"AI 判为 B/C 但你认为该保留"的，单独升为 A 档逐条处理。
5. 分档结果与最终处置一并进 ledger，记录签字时间与 main SHA。

**若频次表窗口不足 30 天**：短窗口会把低频但重要的接口（如月度报表、年度配置）误判为零流量。此时对 B 档额外做一次源码启发式复核——被前端代码引用但零流量的，一律升 A 档人工看，不得直接废弃。
