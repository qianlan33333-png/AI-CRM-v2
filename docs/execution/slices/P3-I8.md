- 官方执行矩阵把 I-8 固定为“待合并页面”；本片只调用 I7 已合的 typed client：

## 可观察行为

- admin/ops 可从主导航进入 `/identity/merge-reviews`，读取 pending review 的服务端 opaque cursor
  列表；页面只展示 Kind、scope、去标识 HMAC、版本与恰好两个排序候选 OneID，不显示 raw identity。
- 选择待办后进入同页审阅区；approve 必须主动选择候选中的主客户并填写 1–500 字理由，reject
  只提交版本和理由，不隐式选择主客户。成功事实从当前列表移除，reject 明确提示客户绑定保持不变。
- 写请求使用 same-origin、CSRF 与稳定 Idempotency-Key；同一表单事实的网络失败重试沿用同 key，
  修改主客户或理由后换新 key。状态码与畸形响应均 fail-closed，不显示服务端异常内容。

## 边界、修正与证据

- 手写业务范围：Identity review Web transport/parse、页面与样式、Web route/permission，共 6 个业务文件；
  测试、browser smoke、slice card、ledger 与 contract hash 同步不计入业务规模，低于 P3 1000 行推荐线。
- `slice_induced=2`：首轮实现补齐 direct transport 的 CSRF token 形状校验；第二阶段自审发现刷新可与
  进行中的 mutation 竞争且会保留旧表单，遂禁用 mutation 期间刷新并原子清空审阅草稿。达到降档阈值后
  范围冻结，均未扩展 I8 既定行为。
- `verification_induced=6`：全新 worktree 首轮缺少 `node_modules`，执行固定锁文件 `npm ci`；激活脚本后
  全局 `prettier` 与 `rg` 不在 PATH，分别改用本地固定 formatter 与未激活的只读搜索；一次只读 checker
  搜索的正则转义不完整，改用 fixed-string 重发；最终收据首次在临时首个 I8 commit 之上 staged 检查时被
  ledger history 正确拒绝，收据随即 amend 回同一业务 commit 后从其父提交重跑；重放验证时激活脚本已切到
  仓库根目录，首次只读脚本查询误用嵌套 `web/package.json`，随即读取实际根 `package.json`。以上均未改变业务实现。
- `infra_induced=1`：旧 base 的 I8 四门全绿后 O5 先合并，PR #193 因累计 ledger/checker 变化转为冲突；
  本片安全重放到 O5 exact-green main，仅逐块同步 ledger 与 checker 收据，最终业务 diff 不含 Outbound 文件。
- 本地验证包含 strict TypeScript、全量 Web unit/render tests、build/audit、503 同 key 重试的浏览器完整流、
  application/go 全门、generated/contract 完整 negative corpus 与 secret gates；GitHub required CI 待 PR 绑定。
- 不执行生产数据库、live migration/cutover、真实企微、W5 接线、真实外发或部署。
