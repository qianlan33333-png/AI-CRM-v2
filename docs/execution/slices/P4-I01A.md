# P4-I01A：普通商品目录与旧后台兼容

## 输入、冻结范围与真实闭环

- Base 为 P4-SI00B exact-green `bdafc833d947caa66b0a6b408c2ca4574f59b3da`；本片从全新隔离
  worktree/branch 重建，历史 I01A HARD STOP 与其他 WIP 永久只读，未复制或 cherry-pick。
- 唯一业务闭环是普通商品 create/list/get，同时真实承接旧后台
  `LEGACY-API-0525/0526/0530` 与旧 UI 动作 `LEGACY-S07-164/165`。Product core 使用 typed
  `product_code`、minor amount、native images 与 `stock_quantity`；旧 UI 未提供库存事实时固定映射
  `stock_quantity=0`，不据此创建库存或可售生命周期。
- create 在一个 UoW 内完成 Product、native image、actor-scoped 幂等 receipt 与
  `product.created` Event；相同 actor/key/canonical payload 精确重放，payload 冲突不复用结果，
  Event 冲突时 Product 与 receipt 一并回滚。

## 旧 DTO 被动投影与外部效果边界

- `status/enabled/buy_button_text/require_mobile/lead*/completion*/wecom_tagging/slices` 只进入
  Product-owned、allowlisted、`schema_version=1` 的 canonical JSONB compatibility projection。
  create→get/list 按 JSON 语义精确 roundtrip；projection 参与幂等 digest，PostgreSQL JSONB
  规范化后仍能重放。
- `slices` 只是被动图片投影，不调用 Media；上述字段不触发生命周期、企微标签、线索、完成跳转、
  支付、退款、订单、发送或任何 provider 调用。兼容成功 envelope 中
  `fallback_used=false`，且 `real_external_call_executed/payment_request_executed/real_wechat_pay_executed/
  real_alipay_executed/provider_signature_verified/real_refund_executed` 均为 false。
- immutable legacy `_raise_http` 的 Contract/NotFound/internal 分类分别是 400/404/500；v2 保留该
  HTTP 分类，但最终响应继续使用现有 platform gateway 的统一 `{code,message,request_id}` 合同。
  黑盒冻结最终响应，不绕过 gateway 伪造旧 `detail`、成功字段或执行字段。

  避免 20 万 Product 主表扫描；list/get 使用 Product 索引。
- 非生产 PG16.14 执行真实 `28→29→28→29`，迁移前 Event、Auth 与 session 表的逐行指纹完整
  保留；Product/receipt/Event 正常、边界、错误、四故障点回滚、并发 canonical replay、异 payload/
  duplicate product code 冲突与触及的 S 档 20 万 `FORMAT JSON` 计划均验证。
- 本片只关闭 `LEGACY-API-0525/0526/0530` 与 `LEGACY-S07-164/165`。`LEGACY-T14-302`
  保持 `ARCHIVE_ONLY/NOT_STARTED/NOT_RUN`，旧表历史导入或处置由后续独立决策片负责，不能用
  新建空目标表冒充历史迁移完成。

## 复用基座、明确未建设与后续减负

- 保留的可复用基座：Product typed core、Product-owned SQLC/store、actor-scoped canonical receipt、
  Event 同 UoW、native OpenAPI/RBAC/CSRF、旧 UI adapter，以及旧/native 两个真实消费者共用的
  exact-total/read model。I02 public product/landing 与 I03 order 可复用 product ID/code/read port，
  无需再次实现目录、兼容 projection、幂等或 Event 原子性。
- 明确未建设：库存/可售状态机、支付/退款、订单、Media/企微/线索/跳转执行、tenant model、
  泛化 commerce 平台、策略权限/风控/审计告警、运维 UI/dashboard、恢复器或新 UI。
- 因此减少的重复工作：后续片只需在各自 owner 内增加真实库存、订单、支付或公开读取能力，
  不再重复商品身份、目录持久化、旧后台 DTO 兼容、幂等与事件 UoW。

## 修正、验证分级与外部门

- `correction_state=SCOPE_FROZEN_REPAIR_ONLY`，`slice_induced=10`、`infra_induced=0`、
  `verification_induced=18`、`redline=0`。继承的两个 scope 修正后，聚焦测试依次发现并修复：
  receipt payload 冲突先被误分类 unavailable、PG JSONB 规范化后仍做字节比较、JSON scalar
  被误识别为 null、exact total 扫描 20 万主表、自定义错误 body 被 gateway 规范化，以及 Product
  测试错误携带已冻结删除的 tenant 语义、JSON 语义比较经 float64 丢失大整数精度，以及
  projection decoder 未严格拒绝对象后的第二个 JSON 值。
  都只修当前冻结片，不扩能力。
- verification 仅记录：fresh worktree 缺 pinned Orval 后按仓库入口 bootstrap；一次误删仍被 decoder
  使用的 import；测试库曾应用迁移的较早未提交修订，先恢复到 28；Event conflict 的内部错误分类
  断言过强；迁移反复回放后 fixture 仅按 product_id 查询不再唯一；staged-index 合同阻止测试重新
  引入 tenant 语义；第二阶段源码自审发现大整数语义精度边界和 trailing JSON 边界。均在提交前以最小重放收口。
- PR 首轮 secret-scan 将测试变量名与纯校验占位值识别为 3 个 generic-api-key；未发现真实密钥，
  仅改为无 key 语义的 replay 引用名与运行时生成占位值，并重写同一 PR 提交以清除旧提交扫描命中。
  首次最小重放发现两个断言仍引用旧局部变量名，随即同步为 replay 引用并重新聚焦验证。
  首轮 Go CI 还发现 P1 candidate-server 方法清单仍是新增 Product 三个 native operation 前的 27 项，
  仅同步该既有防回归合同为 30 项并重跑受影响链。
  第二轮 CI 发现架构导入器域清单尚未登记 Product，且 feature-matrix 合同正负例仍假设 synthetic=0；
