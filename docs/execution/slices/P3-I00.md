## 已冻结决策

### 1. Scope 与规范化

- `customers.id` 仍是唯一渠道中立 OneID；外部标识只存在于 identity 域。
- Kind 固定为 `wecom_external_userid / unionid / mp_openid / oa_openid /
  alipay_user_id / phone / ext`。自定义 provider 放在 `scope=ext:<namespace>`，
  不再同时把 namespace 编进 Kind。
- scope 固定前缀：`wecom-corp:`、`wechat-open-platform:`、`wechat-app:`、
  `phone:e164`、`alipay-app:`、`ext:`。空 scope、未知前缀或 Kind/scope 不匹配
  均在进入 UoW 前拒绝。
- identity 独占原始 value 的规范化。调用方不得 lower-case、E.164 化、拼接或
  建立本地映射。I-1 必须为每个 Kind 冻结版本化 normalizer 与 raw/normalized
  审计边界。

### 2. 可信来源

- `verified` 只能由已验真的内部 provider adapter 构造；浏览器/admin HTTP body
  不得自报 `verified` 或 provider source。P3 admin HTTP 的 ref 只携带
  `type/scope/value`，服务端固定以 `declared/admin` 构造证据。
- WeCom、OAuth、Extension 等后续 adapter 必须在自己的安全片完成验签/凭据校验
  后才可调用 identity port；identity 仍重新校验 Kind、scope 与 source 组合。

### 3. Resolve / Bind / Ingest

- Resolve 结果唯一使用 `found/not_found/conflict` 枚举；`found` 才返回
  `customer_id`，其他状态不泄露候选 ID；禁止隐式建档。
- Bind 状态为 `bound/already_bound/merged/manual_review/rejected`。这些是 200
  业务结果，不用 error 或 409 代替；409 只表示幂等键 payload 冲突或版本并发。
- Bind 与 Ingest 必须有稳定幂等键；同 key 同规范化 payload 返回原事实，同 key
  异 payload fail-closed 且零新增副作用。
- Ingest 的 `attributed` 只返回 customer/event，`pending` 只返回 pending ID，
  `conflict` 不返回候选客户。时间线与 event_log 同事务，pending/conflict 必须
  durable，不能只返回状态。
- Bind merged 结果的 `customer_id` 是同一 UoW 锁定并重验后、执行本次 merge 前的
  请求 customer effective root；`primary_customer_id` 是归并提交后的最终 root。
  `customer.merged` payload 仅含
  primary/merged customer ID、merge audit ID、mode 与 policy version，不含 PII；
  event idempotency key 固定为 `customer.merged:<merge_audit_id>`。

### 4. verified unionid 自动合并

- 只有同一 `wechat-open-platform:<account-id>` scope 的 verified unionid 冲突
  才进入自动合并判定。跨 scope unionid、verified phone、declared phone、openid、
  external_userid 与 ext 均不能触发自动合并。
- 先将输入客户和既有绑定解析到非删除的 effective roots；同 root 返回
  `already_bound`。只允许恰好两个 root 进入本规则，更多 root 为 conflict。
- 主记录规则必须 total、顺序无关且不以 ID 大小猜测业务主记录：恰好一个 root
  拥有至少一条 verified `wecom_external_userid` 时，该 root 为 primary；双方都有
  或双方都没有时创建/复用人工待合并项，返回 `manual_review`，客户与绑定不变。
- 数据库锁仍按较小 customer ID 到较大 ID 获取，只用于避免死锁，不参与 primary
  选择。合并审计记录固定 policy version
  `verified_unionid_unique_wecom_v1`。
- 任何自动合并都通过同一 UoW 调 contact MergePort、重绑 identity、追加
  `customer_merges` 和 `customer.merged` event_log；任一步失败整体回滚。

### 5. 人工待合并与 replay

- verified phone 冲突和 unionid primary 无法唯一判定时创建或复用 review；同一
  规范化证据与 root 集合只能有一个 active review。
- active merge review 恰好包含两个 current roots；三项以上保持 conflict 并转独立
  人工调查，禁止一次 approve 隐式执行 N-way merge。
- 人工 API 冻结 list/approve/reject，均采用版本乐观锁。approve 显式选择
  `primary_customer_id`。approve 必须在同一 UoW 内锁定并重解析 current effective
  roots，确认 review 仍 pending、version 匹配、primary 属于当前候选 root 集，且
  证据与候选集合均未漂移；任一不满足返回 409 且零副作用。reject 不改变任何绑定。
  重复相同命令幂等，版本/命令冲突返回 409。
- review 对外标识固定为 secret-backed versioned HMAC：输入为 Kind、canonical scope
  与 normalized value 的无歧义串，HMAC-SHA256 key 来自 typed secret store，输出
  `hmac-sha256-v<version>:` 加前 128 bit base64url（无 padding）。禁止 raw、normalized、
  无密钥 hash 或 handler 临时计算；I-1 必须冻结 key 创建/轮换和持久化字段。
- `pending_events` 必须区分 attribution、conflict 与 merge_review；review 项永不
  被 pending replay 自动批准。replay 保留原 occurred_at/source/idempotency_key。

  openid、Ingest 三状态、故障注入、反向/成环合并、lineage 读取。

  unionid，提交后只允许一个 effective primary、一个 merge audit、一个

- mock/local/synthetic/真实 provider 证据分开；真实企微与生产迁移继续
